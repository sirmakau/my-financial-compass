# 1. Introduction
This guide explains how to connect incoming M-Pesa SMS notifications on an Android phone to the Ledger application.

The intended workflow is:

```
M-Pesa sends transaction SMS
           |
           v
       Android phone
           |
           v
       MacroDroid
           |
           v
    Internet connectivity check
           |
      +----+----+
      |         |
   Online     Offline
      |         |
      v         v
  HTTP POST   Save SMS to file
      |         |
      v         v
 Supabase    Pending SMS queue
 Edge Function    |
      |            |
      v            v
 Ledger Inbox   Retry when online
```
The integration uses MacroDroid to detect SMS messages and send them to a Supabase Edge Function through an authenticated HTTP request.

The system has two intended capabilities:

1. **Online delivery:** Send incoming M-Pesa messages directly to Ledger.
2. **Offline delivery:** Preserve messages when there is no internet connection and send them when connectivity returns.
The online integration has already been tested successfully. The offline retry mechanism is still being developed.

# 2. Requirements
Before starting, you need:

- An Android phone with a working SIM card receiving M-Pesa SMS messages.
- The Ledger application and access to its phone setup instructions.
- A deployed Supabase Edge Function for receiving SMS messages.
- A private key generated by Ledger.
- An internet connection for initial configuration.
- MacroDroid installed on Android.
You do not need to write an Android application or install a programming environment.

# 3. Obtaining the Ledger Webhook URL
A webhook is an HTTP endpoint that receives information from another application or service.

In this integration, MacroDroid sends an HTTP POST request to Ledger's Supabase Edge Function whenever an M-Pesa SMS arrives.

### Step 3.1 — Open Ledger

1. Open the Ledger application.
2. Navigate to the SMS inbox or phone integration/setup section.
3. Open the phone setup instructions.
4. Locate the webhook configuration.
The configured endpoint for this integration is:

```
https://bnkaqqzumxuozievggtt.supabase.co/functions/v1/sms-webhook
```
This is the destination URL that MacroDroid will call.

### Step 3.2 — Generate the private key
Inside Ledger's phone setup instructions:

1. Locate the private key generation option.
2. Generate a private key.
3. Copy the generated value.
4. Keep it private.
The key authenticates requests coming from your phone.

**Important:** The webhook URL is not the secret. The private key is.

Never publish the key in a screenshot, public repository, social media post, or shared document.

If a previously generated key has been exposed, generate a replacement and update MacroDroid with the new value.

# 4. Understanding the Webhook Request
MacroDroid must send three important pieces of information.

ComponentValueHTTP methodPOSTWebhook URLLedger SMS webhook endpointContent typeapplication/jsonAuthentication headerx-ledger-key
### Step 4.1 — Authentication header
The request must contain this header:

```
x-ledger-key: YOUR_GENERATED_PRIVATE_KEY
```
Replace the placeholder with the private key generated inside Ledger.

Do not include the key inside the URL or JSON body.

This is a custom authentication header used by the Ledger webhook. It is not the same thing as a Supabase service-role key.

### Step 4.2 — JSON request body
Ledger expects the following JSON structure:

```
{
  "message": "M-Pesa SMS content goes here",
  "sender": "MPESA"
}
```
The two values are supplied dynamically by MacroDroid:

- `message`: The actual SMS content.
- `sender`: The SMS sender identifier or number.
For example, MacroDroid should send something conceptually similar to:

```
{
  "message": "Confirmed. Ksh 500.00 sent...",
  "sender": "MPESA"
}
```
The real message will vary with each transaction.

### Step 4.3 — Supabase backend considerations
The Supabase Edge Function receives the HTTP request and handles the database operation.

The private key should be checked on the server side. It should never be embedded in publicly accessible frontend code.

If managing the Edge Function yourself, store server-side credentials using Supabase Function Secrets rather than hardcoding them.

Official documentation:

- [https://supabase.com/docs/guides/functions](https://supabase.com/docs/guides/functions)
- [https://supabase.com/docs/guides/functions/secrets](https://supabase.com/docs/guides/functions/secrets)
- [https://supabase.com/docs/guides/functions/auth](https://supabase.com/docs/guides/functions/auth)

# 5. Downloading and Installing MacroDroid
MacroDroid is an Android automation application that uses three main concepts:

- **Triggers:** Events that start an automation.
- **Actions:** Operations performed after a trigger.
- **Constraints:** Conditions that must be satisfied before an automation runs.

### Step 5.1 — Download MacroDroid
Open Google Play Store.

Search for:

```
MacroDroid - Device Automation
```
Check that the developer is ArloSoft.

You can also open:

[https://play.google.com/store/apps/details?id=com.arlosoft.macrodroid](https://play.google.com/store/apps/details?id=com.arlosoft.macrodroid)

Install the application and open it.

Avoid downloading modified or unofficial APK files.

### Step 5.2 — Initial permissions
MacroDroid requires permissions for the features you intend to automate.

For this integration, the important permissions include:

- SMS permission, so incoming SMS messages can trigger macros.
- Network access, so HTTP requests can reach Ledger.
- File access through Android's storage picker, so offline messages can be saved and read.
- Notification permission, which is useful for automation alerts and troubleshooting.
Grant the permissions when Android requests them.

You do not need to grant every optional permission simply because MacroDroid requests it.

### Step 5.3 — Allow background operation
Android manufacturers sometimes restrict applications running in the background.

Check your phone's battery management settings.

Where available:

1. Open Android Settings.
2. Find Apps or App Management.
3. Select MacroDroid.
4. Open Battery settings.
5. Allow unrestricted background activity or disable battery optimisation for MacroDroid.
On some devices, you may also need to allow MacroDroid to start automatically.

The exact menu names vary by manufacturer.

This is important because the automation must remain available when the phone is locked or MacroDroid is not open.

# 6. Creating the Main Ledger Macro
This macro detects incoming M-Pesa SMS messages.

Its responsibility is to decide whether to send a message immediately or store it for later.

### Step 6.1 — Create the macro

1. Open MacroDroid.
2. Navigate to Macros.
3. Tap the plus button.
4. Create a macro named:

```
Ledger
```

### Step 6.2 — Configure the trigger
Under Triggers:

1. Select Add Trigger.
2. Open Messaging.
3. Select SMS Received.
4. Choose the sender `MPESA`.
5. Set content matching to `Any Content`.
6. Save the trigger.
Your trigger should look like:

```
SMS from MPESA
Any Content
```
This tells MacroDroid to run the automation whenever a matching M-Pesa SMS arrives.

The SMS Received trigger also provides Magic Text values for the sender and the received message.

### Step 6.3 — Create the connectivity variable
Before checking connectivity, create a global Boolean variable.

Go to Variables and create:

SettingValueScopeGlobalNameinternet_availabilityTypeBooleanThe variable will hold either:

- `True`: Internet connectivity is available.
- `False`: Internet connectivity is unavailable.

### Step 6.4 — Add Connectivity Check
Under Actions:

1. Open Connectivity.
2. Select Connectivity Check.
3. Configure the following:
SettingValueURL[www.google.com](http://www.google.com/)Timeout5000 msSave to variableinternet_availabilityBlock next actions until completeEnabledThe action checks whether the phone can reach the internet before proceeding.

Using a connectivity check is better than simply checking whether Wi-Fi or mobile data is switched on.

### Step 6.5 — Add the If condition
Open Conditions/Loops and add an If condition.

Configure:

```
internet_availability = True
```
The macro should now have two possible execution paths.

# 7. Configuring the Online HTTP Request
Inside:

```
If internet_availability = True
```
add an HTTP Request action.

Open the HTTP Request configuration.

### Step 7.1 — Request settings
Configure:

SettingValueMethodPOSTURL[https://bnkaqqzumxuozievggtt.supabase.co/functions/v1/sms-webhook](https://bnkaqqzumxuozievggtt.supabase.co/functions/v1/sms-webhook)Content typeapplication/json
### Step 7.2 — Add the authentication header
Under Header Parameters, add:

Header nameHeader valuex-ledger-keyYour generated Ledger private keyMake sure the header name is exactly:

```
x-ledger-key
```

### Step 7.3 — Configure the request body
The request body should follow this structure:

```
{
  "message": "{sms_message}",
  "sender": "{sms_number}"
}
```
The curly-bracket values represent MacroDroid Magic Text.

Do not assume that manually typing those placeholder names will work in every version of MacroDroid.

Use the Magic Text picker:

1. Tap the button beside the body field.
2. Select Incoming SMS message.
3. Insert the message into the JSON `message` field.
4. Open Magic Text again.
5. Select Incoming SMS number.
6. Insert it into the JSON `sender` field.
The resulting body must contain the two dynamic values.

### Step 7.4 — Save the HTTP Request
Save the action.

Your online execution path should now be:

```
If internet_availability = True
    HTTP Request (POST)
        Ledger webhook URL
        x-ledger-key
        application/json
        SMS message
        SMS sender
End If
```
The original online request was tested with a real M-Pesa SMS, and the message appeared in the Ledger website.

# 8. Configuring Offline SMS Storage
The internet may occasionally be unavailable.

Instead of losing the SMS, the Else branch stores it locally.

### Step 8.1 — Add an Else clause
Inside the main If condition:

1. Tap the If action.
2. Open its configuration menu.
3. Select Add else clause.
The structure should become:

```
If internet_availability = True

    HTTP Request (POST)

Else

End If
```

### Step 8.2 — Create the storage folder
Open Files and select:

```
File Operation (Storage Framework)
```
Use Android's folder picker to create or select:

```
Ledger
```
This folder will hold the pending SMS file.

### Step 8.3 — Create the pending SMS file
Inside the Else branch:

1. Add Action.
2. Open Files.
3. Select Write to File.
4. Select Storage Access Framework.
5. Select the Ledger folder.
6. Configure the filename:

```
pending_sms.txt
```

1. Select Append to file.
Append is important because it preserves previous messages instead of replacing them.

### Step 8.4 — Configure the stored SMS format
The configured record format is:

```
{sms_number}|{sms_message}
~#LEDGER_END_7F3A#~
```
Use MacroDroid's Magic Text picker for:

- Incoming SMS number.
- Incoming SMS message.
Type the separator and record marker as ordinary text.

The marker identifies where one queued record ends.

A conceptual example:

```
MPESA|Confirmed. Ksh 500.00 sent...
~#LEDGER_END_7F3A#~
```
Each incoming offline SMS is appended to the same file.

### Step 8.5 — Save and verify
Save the Write to File action.

The main macro should now have this arrangement:

```
SMS from MPESA

Connectivity Check
    www.google.com
    internet_availability

If internet_availability = True

    HTTP Request (POST)
        Send SMS to Ledger

Else

    Write to File
        pending_sms.txt
        Append to file

End If
```
Save the macro and enable it.

# 11. Important: Complete and Validate Offline Retry Before Enabling It
The queue and replay process must be completed carefully.

There are several important requirements.

### A. Extract each SMS separately
Inside the array loop, use:

```
{iterator_value}
```
as the current record.

The record contains the sender and message separated by a pipe character.

The next processing stage must extract:

- Sender.
- Message body.
Do not send the whole file as a single HTTP request.

### B. Send one HTTP request per record
For each extracted record, issue an HTTP POST using the same webhook URL, key header, and JSON structure as the main macro.

Each SMS must be delivered separately.

### C. Check the response
The HTTP Request action can save the response status code into an integer variable.

Use that status code to determine whether the request succeeded.

A successful HTTP response alone does not prove that the database inserted the message correctly, so the Edge Function should return an appropriate success response only after processing has succeeded.

### D. Protect against duplicate transactions
This is particularly important for financial SMS messages.

Imagine the following situation:

1. MacroDroid sends a queued SMS.
2. Ledger stores it successfully.
3. The phone loses connection before receiving the response.
4. MacroDroid assumes that delivery failed and sends the SMS again.
Without duplicate protection, one transaction could appear twice.

The backend should therefore have an idempotency or duplicate-detection mechanism before automatic retries are enabled.

### E. Clear the queue only after successful delivery
Do not delete or overwrite the pending file simply because the macro has started.

The file should only be cleared or updated after all relevant records have been delivered successfully.

If a request fails, the undelivered records must remain available for a later retry.

**Until these conditions are implemented and tested, leave **`Ledger - Offline Sync`** disabled.**

# 12. Testing the Integration
Testing should happen in stages.

## Test 1 — Online delivery

1. Make sure mobile data or Wi-Fi is connected.
2. Confirm that the `Ledger` macro is enabled.
3. Wait for a legitimate M-Pesa SMS.
4. Check that the main macro triggers.
5. Open Ledger's SMS inbox.
6. Confirm that the received transaction appears.
Expected result:

```
Incoming M-Pesa SMS
       |
MacroDroid detects SMS
       |
Connectivity Check = True
       |
HTTP POST
       |
Ledger Inbox receives message
```
This basic online path has already been tested successfully.

## Test 2 — Offline storage
Only test this after confirming that the file-writing action works.

1. Ensure the main macro is enabled.
2. Temporarily disconnect the phone from the internet.
3. Receive a suitable test SMS.
4. Check that the connectivity result is False.
5. Confirm that the Write to File action executes.
6. Inspect `pending_sms.txt` and verify that the sender and message were saved.
Do not rely on the file being written merely because the macro ran. Inspect the actual contents.

## Test 3 — Retry delivery
This test should only be performed after the offline sync macro has been fully implemented.

1. Put the phone online.
2. Confirm that the connectivity check succeeds.
3. Allow the sync macro to process the queued records.
4. Check the HTTP response status for each request.
5. Confirm that each record appears exactly once in Ledger.
6. Verify that successfully delivered records are removed from the queue.
7. Confirm that failed records remain available.

# 14. Security Recommendations
Because the webhook can insert financial transaction information, security matters.

1. Keep the Ledger private key confidential.
2. Rotate any key that has been exposed.
3. Never publish the key in a GitHub repository.
4. Do not use a Supabase service-role key as a substitute for the Ledger private key.
5. Keep webhook authentication on the server side.
6. Avoid sharing screenshots showing the authentication header.
7. Add duplicate detection to the backend before enabling automatic offline retries.
8. Test with controlled messages before relying on the automation.
